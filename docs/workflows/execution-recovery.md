# [5,0,8,0,1] Execution Recovery

Status: **Command Commit Guard, local durable Execution Ledger admission and conservative account-scoped reconciliation are implemented in Python**. Full recovery orchestration, State Integrity, Interrupt Control and the complete pipeline remain outstanding. The [implementation guide](../architecture/durable-execution-recovery.md) specifies supported topology, stronger ledger contracts, restart rules and current provider-evidence limitations. These components do not activate a live trading service.

Execution Recovery is the broker-neutral durability and reconciliation layer for Execution Engine.

It exists to answer one question before any uncertain action is repeated:

> What actually happened at the broker?

## Core invariant

**Never blindly retry a broker mutation whose outcome is unknown.**

Timeout, disconnect, process crash or missing acknowledgement means RECONCILE, not RETRY.

## Runtime identity versus VID

VIDs identify architecture.

Live execution uses separate runtime identities.

### [5,0,1,7,3] Runtime Intent Identity

Conceptually:

~~~text
intent_id
intent_version
supersedes_version
created_at
status
~~~

Every ordering plan, slice, execution action and broker correlation must remain attributable to the runtime intent/version that created it.

If an upstream strategy or Strategy Execution Adapter supersedes an intent, stale actions generated by an older version must be rejected before broker submission.

## [5,0,8,9,1] Execution Ledger

The durable ledger links:

~~~text
runtime intent/version
    ->
execution slice
    ->
execution action
    ->
correlation / broker order IDs
    ->
trades / fills
    ->
authoritative position effect
~~~

The ledger must survive process restart.

It is the source of execution history, not the source of broker truth. Broker truth remains authoritative.

## [5,0,8,7,1] Execution Action Envelope

Every mutating broker action is wrapped in a broker-neutral envelope containing at least:

~~~text
action_id
action_class
origin_type
origin_id
intent_id / intent_version when applicable
slice_id when applicable
correlation_id
requested operation
created_at
~~~

Interrupt-originated emergency actions can use interrupt identity rather than a normal intent identity.

## [5,0,8,1,2] Command Commit Guard

All broker-mutating actions pass through this guard, including:

- Passive Chase actions;
- future Optimal Execution algorithms;
- interrupt cancellation;
- interrupt emergency flattening.

Before release to the Broker Execution Port it:

1. validates that the originating intent/version is still current when applicable;
2. rejects stale/superseded actions;
3. checks interrupt-latch compatibility;
4. checks State Integrity permission for the action class;
5. creates/validates a unique correlation identity;
6. records the intended action durably in the Execution Ledger;
7. only then releases the mutation.

The write-ahead record therefore precedes the broker mutation.

## [5,0,8,1,1] Reconciliation Engine

Consumes the ledger plus authoritative broker facts.

It resolves:

- acknowledgement missing after submit;
- timeout after mutation;
- partial fill ambiguity;
- cancel/modify races;
- restart with live broker orders;
- restart with fills not yet reflected locally;
- duplicate/missing trade observations;
- difference between requested and actual position effect.

It produces [5,0,8,7,2] Reconciliation Result.

## [5,0,8,2,1] Recovery State

Current states:

~~~text
CLEAN
RECONCILING
AMBIGUOUS
RECOVERY_REQUIRED
~~~

Normal new mutations in an affected scope are blocked while broker truth is unresolved.

On restart, Execution Engine reconstructs execution truth from durable ledger + broker orders/trades/fills/positions before resuming normal execution.

## Supersession example

~~~text
intent I / v1 = BUY 100
40 fill

The upstream strategy emits:
intent I / v2 = target only +20
v2 supersedes v1
~~~

Any unsubmitted or delayed action generated under v1 is stale and must be rejected.

The Reconciliation Engine first establishes actual broker position/order state. Only current v2 requirements may then create new execution work.

## Broker boundary

Provider-specific correlation mechanics, broker order IDs and query APIs remain in the provider adapter.

The recovery policy itself is broker-neutral and belongs here.
